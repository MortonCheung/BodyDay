# 03 · 人体拆解可行性（BodyDay V2）

## 1. 为什么必须换掉「在 Vanatome 之上加适配层」这条路

`@vixotic/vanatome-react@0.1.6` 的全部公开导出里，
`VanatomeController` 只能做 `select / focus / isolate / reset / setVisibleLayers / toggleLayer`，
`displayMode`、`hiddenIds`、`appearance` 只能改显隐与外观。
**不存在任何访问内部场景图 / 网格对象 / 部件位移的入口。**
因此「保留 Vanatome + 自行增加拆解适配层」在当前依赖下不可实现，
除非 fork 依赖源码——而任务书 §6.2 明确禁止大规模侵入依赖源码。

（已在 `00_BASELINE_AND_FEASIBILITY.md` §3.2 逐行核实，此处不再重复取证。）

## 2. 首选路线（Human Atlas）的 go / no-go 实测结论：**no-go**

按要求把参考项目真实克隆到本地核对（不是只读文档）：

git clone --depth 1 https://github.com/ashemag/human-atlas.git   →  154 MB

### 2.1 实测数据

| 核对项 | 实测结果 |
|---|---|
| 依赖版本 | `three ^0.159.0`、`react 19.2.6`、`vite 8.0.13`、`typescript 5.9.3`、`engines.node >= 22.13` |
| 是否使用 R3F | **否** —— `@react-three/fiber` / `@react-three/drei` 均未声明，`app/scene.tsx` 是命令式 three.js |
| 关键文件 | `app/scene.tsx`、`app/explosion-layout.ts`、`app/anatomy.ts`、`app/page.tsx`、`public/ATTRIBUTION.md`、`LICENSE` **全部存在**（与任务书 §6.1 所列一致） |
| 资产体积 | 仓库 154 MB，其中 `public/` **90 MB** |
| 许可 | 应用代码 MIT；几何数据 BodyParts3D 4.0，**CC BY 4.0**（README 原文：「Geometry is merged into batches. Per-structure GPU textures control translation, visibility, and selection.」） |
| 几何规模 | 2,234 个可选网格 / 约 2,288,268 三角形 / 约 33 MB 压缩几何（其 README 声明） |

### 2.2 判定受阻的四条客观理由

1. **渲染范式不同**：它是命令式 three.js，本工程是 R3F 9 全套结构。接入它意味着在同一工程里并行维护两套渲染范式。
2. **three 主版本不同**：`0.159` vs 本工程 `0.186`。同一进程只能有一份 three：要么降级本工程 three（波及 Vanatome、R3F、drei 与现有 41 项测试），要么把它的渲染核心改写到 0.186（即实际上重写它）——两者都与「不 fork、不重写、小步可回退」的纪律冲突。
3. **资产与 ID 双轨**：新增 90 MB 另一套整具人体资产（BodyParts3D / CC BY 4.0）与另一套结构 ID 体系，需要手工建立 → BodyDay 实体的映射（任务书 §4.2 的全部工作量），并与现有 Z-Anatomy（CC BY-SA 4.0）形成两套人体、两套许可、两套坐标系。这与任务书 §2.2「不长期同时加载 Vanatome 和 Human Atlas 两套完整人体场景」直接冲突。
4. **它的"拆解"机制不可直接搬运**：合批几何 + 逐结构 GPU 状态纹理平移，是对其自有打包格式与自定义着色器的强耦合；不搬运其几何打包管线就拿不到可驱动的平移，搬运则等于接管它整套构建脚本（Python + Node 压缩流程）。

⇒ 按任务书 §2.4 的授权，**首选判定为 no-go，切换备选方案**。

## 3. 备选方案（选中）：atlas 自有整具人体 + 自建 R3F 拆解舞台

### 3.1 为什么这条路线成立（全部为实测）

`catalog.json` 的 `defaultProfileId` 就是 `full-body`，其 bundle `curated-full-body` 是**一个文件里的整具人体**：

- 30.4 MB（二进制 29.2 MB / JSON 1.3 MB）
- 984 个节点、984 个网格、984 个图元、64 个材质
- **1,746,560 三角形**、972,475 顶点（比 Human Atlas 声明的 2,288,268 三角形少约 23%）
- **984 / 984 节点带 `extras.anatomyId`**；748 个带 `extras.anatomyParentId`；
  **968 / 984 节点带 `translation`** ⇒ 逐节点真实位移成立
- 节点名 `<结构ID>__<解剖英文名>` ⇒ 可读名称随模型自带
- 材质名 `vanatome__<结构ID>` ⇒ 材质按结构分组，便于共享与高亮
- 覆盖全部 11 个系统（体表 236、神经 234、骨骼 181、肌肉 170、循环 64、淋巴 54、生殖 14、消化 12、内分泌 10、呼吸 6、泌尿 3）
- **同一许可（CC BY-SA 4.0）**、**同一 ID 体系**、**同一依赖（three 0.186 + R3F）** ⇒ 不新增引擎、不新增资产来源、不新增 ID 映射工作量

### 3.2 拆解的实现机制（本作品自建，非复制第三方）

1. 用 drei 的 `useGLTF` 加载整具人体 GLB（支持 `VITE_BODYDAY_ATLAS_URL` 指向自建镜像）。
2. 遍历场景，按 `node.userData.anatomyId`（即 glTF `extras`）建立
   **`anatomyId → 该节点的网格集合`** 索引；再用 `extras.anatomyParentId` 回溯，
   把后代网格归并到器官级结构（与现有 `buildStructureEntityIndex` 同思路）。
3. 位移方向**由真实几何确定**：
   - 计算每个结构组的世界包围盒中心；
   - 方向 = 从人体纵轴（由全体网格包围盒求出的中轴）指向该组中心，取其**径向分量**并保留少量向上分量；
   - 位移距离按该组自身尺寸与所属系统分层定标，**不使用随机向量**。
4. `explosionProgress ∈ [0, 1]` 连续插值（缓动），0 = 组装态且**人体轮廓仍可辨认**，
   1 = 目标拆解布局（结构之间不重叠、不随机飞散）；反向滚动连续复原。
5. 拆解态下仍可点选：网格保持原有 `userData.anatomyId`，Raycast 命中后归并到结构 ID。
6. 高亮与聚焦：悬停/选中时替换该组网格的材质（共享高亮材质，不逐网格克隆）；
   聚焦用该组**真实包围盒**计算相机目标与距离。
7. 组装/拆解反复操作时，位移量始终由 `explosionProgress` **重新计算**而非累加，
   因此不会产生累计偏移。

### 3.3 风险与如实标注

- 984 个网格 = 984 次绘制调用（无合批）。本作品的处理：按图层显隐裁剪可见组
  （初始只显示体表 + 骨骼），并对同材质网格复用材质实例。
- 本机只能以 headless + SwiftShader 软件渲染验收，
  **无法采集真实 GPU 帧率**；报告中必须标注为「软件渲染环境，真实 GPU 性能未测」。
- 冷启动体积从当前的「体表 6.3 MB + 骨骼 3.9 MB = 10.2 MB」变为
  **一次 30.4 MB**；但可完全取消按系统分别加载（原本每次进入系统还要 3.9～11.3 MB）。
  真实冷启动秒数按本机实测记录，不用估算值。

## 5. 若验证失败的诚实协议（预备，不预设失败）

若备选方案在实机验证中出现不可解决的阻碍（例如位移无法连续驱动、点选与结构 ID 无法对应、
单一 Canvas 无法稳定承载 984 网格）：

1. 保留其它已完成的 V2 功能，不整体停摆；
2. 留下**可复现**的失败证据（日志、截图、最小复现步骤）；
3. 记录阻碍与后续建议；
4. **明确标注「需求四 · 人体拆解 P0 未完成」**；
5. 可以提供具有真实科学意义的渐进显影作为临时替代，但**不得称为真实拆解，也不得计入需求四完成**。
