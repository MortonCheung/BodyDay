# BodyDay（身体的一天）· 作品开发文档

**赛道**：2026 辽宁省大学生科普设计大赛 · 非医类健康科普赛道 · 第 4 组（健康科普小程序、H5 交互式和电子杂志设计）

**作品形态**：H5 交互式网页作品（单页应用，一个空间工作台，11 个可独立直达页面）

**作品名称**：BodyDay · 身体的一天

---

## 一、需求分析

### 1.1 问题

面向大众的健康科普长期存在两个断层。第一是**尺度断层**：公众熟悉的科普材料要么停在「人体有多少块骨头」的宏观层面，要么直接跳到细胞名词表，中间「器官—组织—细胞—细胞结构」的层级被压缩成一张平面插图，读者很难建立空间上的连续感。第二是**关系断层**：许多通俗材料把「器官里有这种细胞」当作默认结论，不做区分，结果制造出「心脏生产白细胞」「脾脏制造免疫细胞」这类流传甚广的误解。

对青少年与普通读者而言，更实际的需求不是记住更多名词，而是理解**结构与功能的对应关系**，并把它接到可执行的健康行为上——这正是国家卫健委《中国公民健康素养——基本知识与技能（2024 年版）》所强调的方向。

### 1.2 目标

BodyDay 的目标是提供一件**可探索、可教学**的交互式科普作品：

1. **一个工作台**：中央始终是唯一一具可转动的真实三维人体，右侧是一条随选中联动的知识纸条。用户不必在页面之间来回跳转，就能从人体一路看到细胞；结构的选择完全交给模型本身（点选 / 聚焦 / 隔离 / 逐层拆解）。
2. **跨尺度连续**：从完整人体出发，逐层进入系统 → 器官 → 细胞，全程可原路返回（层级栈）；尺度变化由**镜头位置与右侧纸条内容**表达，而不是换一套页面外壳。
3. **关系语义化**：结构隶属、功能相关、循环输送、疾病语境、尺度延伸分别登记并显式展示，明确拒绝「所有器官 → 任意细胞」的自动兜底关系。
4. **健康科普落地**：每条路线都回答「这个结构如何工作 → 与什么健康行为或常见问题相关 → 可以采取什么有依据的认识」，并逐条标注来源。
5. **科学边界清晰**：明确声明模型为科普示意、不按真实比例、标注点未做逐点配准，作品不构成医疗建议。

### 1.3 目标用户与场景

- 中学生与大学生：具备基本的生物常识，愿意自己动手探索，但不满足于静态插图。
- 科普教师与家长：需要一个可演示、可提问、可检验理解的现成教具。
- 使用场景：桌面浏览器（课堂演示、自主学习）与手机浏览器（碎片时间浏览）。

### 1.4 功能需求（P0 / P1）

**P0（必须实现）**：一个空间工作台（中央唯一真实三维人体 + 右侧随选中联动的知识纸条）；启动封面闸门（真实字节进度 → 模型就绪 → 手动进入）；人体层 / 系统层 / 器官层 / 细胞层四个尺度的模型；结构科学与健康知识卡；可信的结构 ID 映射；模型驱动的点选 / 聚焦 / 隔离 / **滚轮驱动的逐层真实拆解**（V2.1）；器官 → 细胞的跨尺度链路；加载 / 错误 / 重试 / 资源不可用状态；移动端操作；减弱动态偏好支持；中文主界面。

**P1（尽量实现）**：右纸条上的关系浏览（随选中联动）、学习进度与已发现结构记录、内容来源与术语解释。

**明确不做**：原「寝室生活模拟」场景、人物漫游、虚构医学参数预测、医疗诊断、从零重建全部人体器官、全器官全细胞强行覆盖、AI 聊天、用户登录与复杂后端、无授权模型拷贝、用截图冒充实时交互。

### 1.5 竞品对比与取舍

对比对象限定在「公开可访问的人体/细胞科普交互作品与开源查看器」，评价维度为本作品需要解决的四个断层。

| 对象 | 尺度连续 | 关系语义 | 教学能力 | 许可与可溯源 | BodyDay 的取舍 |
|---|---|---|---|---|---|
| BioDigital / 商业解剖应用 | 强（商业体渲染） | 弱（关系多为并列） | 弱（偏浏览） | 闭源、需授权 | 不采用：授权与成本不可控；本作品只需示意级结构 |
| Zygote Body 等在线人体 | 中 | 弱 | 无 | 闭源 | 参考其「层级 + 隔离」交互思路 |
| OpenStax 等开放教材插图 | 无 3D | 中 | 有章节 | CC BY | **采用为知识来源**（S01–S05、S19），但插图不满足交互需求 |
| Vanatome（开源人体查看器） | 强（真实图谱） | 无 | 无 | 代码 MIT / 资产 CC BY-SA 4.0 | **采用其同源的 Z-Anatomy 整具人体资产**（CC BY-SA 4.0）作为数据基础；其查看器封装（`@vixotic/vanatome-react`）因不支持真实网格位移而在 V2 移除，改由本作品自建 R3F 舞台渲染，并自行补齐关系、教学与视觉系统 |
| 各类开源细胞模型仓库 | 仅细胞层 | 无 | 无 | 多为许可不明 | **不采用模型**，改为自研程序化细胞几何 |
| 医学教育类 App/游戏 | 有 | 中 | 有测验 | 闭源 | 参考「交互完成判定 + 即时反馈」的教学结构 |

**结论**：现有作品在「单点能力」上往往很强，但**同时具备跨尺度连续、关系语义化、可教学与可溯源许可**的作品很少。BodyDay 的定位不是做一个更强的人体查看器，而是把成熟的解剖数据重新组织成一件**以关系与尺度为核心的科普教学作品**；而「一个工作台」的形态，让用户不必在页面之间跳转即可完成从人体到细胞的连续观察。

## 二、概要设计

### 2.1 总体结构与产品形态

作品为单页应用（SPA），使用 HashRouter 提供 **11 个可独立直达的页面**。与传统的「多页面 + 每页一个舞台」不同，BodyDay 采用**一个空间工作台（single spatial workbench）**：

- 中央永远是**同一具真实三维人体**（本作品自建的 React Three Fiber 舞台渲染，Three.js r186 + R3F 9 + Drei 10，直接加载随包发布的 Z-Anatomy 整具人体 GLB）；
- **右侧一条知识纸条**，随「当前选中」联动（**V2.1**：所属系统 / 它是什么 / 它如何工作 / 与健康的关系 / 继续深入；尺度轴、秒级时钟、层级目录与重复的取消按钮已删除）；**没有左侧结构目录**；
- 用户点中间模型上的结构 → 右纸条内容随之变化；点模型空白处或按 **Esc** → 取消选中、其余结构恢复、**相机回到选中前的视角**（V2.1）；
- **V2.1**：人体总览未选中时由**滚轮**逐层拆解 / 反向组装（桌面端不再显示拆解滑杆，触屏保留）；选中是**高亮 + 其余结构淡化**而非隐藏；
- 人体 → 系统 → 器官 → 细胞之间的差别，只体现为**镜头位置与右纸条内容的变化**，不换页面外壳、不重挂三维场景。

首页 `/` 先出**完整独立的启动封面闸门**（暖白，与主界面同一视觉语言）：封面内显示模型**真实字节进度**（31.8 MB），模型「装配完成 + 首个有效帧」后才出现「进入探索」；**不自动进入、不自动淡出**，进入前整个外壳 `inert` 且不可读屏（状态机 `loading → ready-to-enter → entering → exploring`）。深链 `/body`、`/organ/*`、`/cell/*`、`/about` 不经过封面。

### 2.2 功能模块层次

```
启动封面闸门（真实字节进度 → 就绪 → 手动「进入探索」；进入前外壳 inert）
应用外壳（品牌 / 「关于」 / 应用级错误边界）
  ├─ 路由解析 resolveView（URL → 视图：body/system/organ/cell/about）
  ├─ 空间工作台 ExploreWorkbench
  │    ├─ 中央舞台 FullBodyStage / CellStage（单活跃 WebGL 场景，舞台级降级边界）
  │    └─ 右侧知识纸条 KnowledgePaper
  │         ├─ 「所属系统」区块（随选中联动；V2.1）
  │         ├─ 「它是什么」区块
  │         ├─ 「它如何工作」区块
  │         ├─ 「与健康的关系」区块
  │         └─ 「继续深入」区块（尺度延伸 / 下钻入口）
  └─ 封底阅读页 AboutPage（canvas = 0，不加载三维）
领域数据层（实体 / 系统 / 关系 / 内容资产脚本 / 来源，纯数据、可单测）
服务层（anatomyModel 模型地址 / atlas ID 映射 / 学习记录）
三维层（FullBodyStage 自建人体舞台 / 细胞舞台 / 程序化几何 / 按需加载入口）
```

### 2.3 跨尺度模型与「尺度的表达」

作品在界面上的尺度分为四层：**人体 → 系统 → 器官 → 细胞**；右侧纸条的「继续深入」区块说明当前所在尺度与可继续深入的链路（不列出没有对应模型的层级）。作品明确区分两种连续性：

- **同模型内的空间连续**：人体 → 系统 → 器官，是在同一个解剖模型中把镜头推进 / 换图层 / 隔离该器官，空间关系真实保留；
- **跨模型的语义连续**：器官 → 细胞，是两个不同模型之间的切换；作品**不声称**几何坐标严格配准，尺度变化由镜头运动本身表达。

> 早期版本曾用一块全屏的「尺度遮罩」来交代尺度切换，现已删除；尺度变化改为更依赖镜头本身与右侧纸条内容的变化。

### 2.4 数据设计

见第三章「核心关系数据」与「领域数据契约」。全部内容为纯数据，可逐条核对与扩展。

### 2.5 视觉与动效设计

采用「暖纸 + 解剖图册」体系：暖白纸面（`#F7F5F1`）与近黑墨色（`#1A1917`），展示层用衬线（系统中文字体栈），正文用系统无衬线，标签用等宽；界面直角优先、以细线分隔，视觉主角始终是三维对象本身；彩色只承担解剖系统与尺度的语义，不作装饰。禁止霓虹科技大屏、玻璃拟态与无意义粒子。V2 进一步把解剖模型上的**体表 / 骨骼 / 肌肉三个系统统一到暖调（象牙 ↔ 陶土）**，内脏保留资产自带的真实解剖配色——这既与暖白纸面同属一套语言，也属于 CC BY-SA 4.0 要求「标明修改」的一部分（已在 `/about` 与 `public/models/ANATOMY_LICENSE.txt` 说明）。

动效只保留五类有解释力的动画：Hover（可否操作）、Selection（当前选中）、Route（进入/返回，作用于右侧纸条的纸张式揭起）、Camera（空间移动）、Scale（尺度变化由**镜头运动本身**表达；**V2.1** 已删除右侧纸条上的尺度轴 / 跨尺度指示）。判据是「删掉这段动画，用户是否更难理解我在哪一层 / 这是不是同一个对象」。`prefers-reduced-motion` 下全部降级为瞬时。

### 3.2 核心关系数据

作品共登记 **14 条**科学关系，覆盖 **5 种**关系类型。所有关系端点均为已登记实体，且每条关系都写明自身的科学语义与依据来源。

| 关系类型 | 含义 | 示例 |
|---|---|---|
| `part_of` 结构隶属 | 一种结构在解剖层级上从属于另一种 | 心脏 → 循环系统；脾脏 → 淋巴系统 |
| `functional` 功能相关 | 功能上相互关联，不表示「拥有」 | 脾脏 → 白细胞（免疫应答场所，白细胞主要在骨髓生成） |
| `circulates_through` 循环输送 | 通过循环被运输到该处，**不代表在此生成** | 心脏 → 白细胞（心脏提供动力，不生成白细胞） |
| `disease_context` 疾病语境 | 仅在明确疾病机制下成立 | 高血压 → 心脏负担；睡眠不足 → 认知功能 |
| `extends_to` 尺度延伸 | 从当前尺度向下进入更小尺度 | 大脑 → 神经元（神经组织相关细胞） |

**三条必须说准确的关系**（同时是自动化测试的断言对象）：

1. 「大脑 → 神经元」：表示脑的神经组织中含大量神经元且类型多样，**不表示**某个脑区只有一种神经元。
2. 「脾脏 → 白细胞」：是**功能相关**，脾脏是免疫细胞聚集与应答的重要场所之一；白细胞主要在骨髓生成。
3. 「心脏 → 白细胞」：是**循环输送**，白细胞随血液流经心脏并被输送到全身；心脏提供动力，**不生成**白细胞。

作品**不使用**任何自动生成的兜底关系；器官到细胞只允许上述三条明确登记的组合（由测试强制）。

### 3.3 关键技术一：自建三维舞台与真实拆解

**单工作台**。`src/app/resolveView.ts` 把 URL 解析成一个视图对象，`AppShell` 只用**同一个** `<ExploreWorkbench view={view}/>` 渲染所有探索页面，不使用 `<Routes>` 声明多条路由。原因是：若每个页面各自声明一条 Route，路由切换时 React 会卸载并重新挂载舞台，造成「地图先归位、再重新聚焦」式的画面跳动，也会重复加载模型。统一解析路径 → 同一棵组件树只更新 props，**三维场景在整段探索中始终挂载**。

**自建舞台而非第三方查看器**。V2 从渲染路径移除了 `@vixotic/vanatome-react`：其公开 API 只提供 select / focus / isolate / reset / visibleLayers，**没有网格位移入口**，无法实现需求四要求的真实拆解。作品改由自建的 React Three Fiber 舞台 `FullBodyStage` 直接加载整具人体 GLB，从而能拿到每个真实网格并逐组位移。

**镜头取景**。atlas 元数据里的 `position` 只是**兜底锚点，并不在渲染坐标系中**；早期用它在外部推算机位会把相机放进网格内部，导致画面全黑。现在的做法是「选中并请求聚焦目标结构」，由舞台遍历真实网格算包围盒来决定机位：

- 全身取景用 `body-shell`（区域解剖中唯一覆盖整具人体、含 236 个网格的结构）；
- 系统取景用该系统的**根结构**（如 `nervous-system`），运行时从已加载清单中取；
- 器官取景用 `cerebrum` / `heart` / `spleen`。

**真实几何拆解（需求四）**。舞台读取 GLB 的 `extras`（`anatomyId` / `anatomyParentId` / `anatomySystem`），按可位移结构组对**真实网格位置**做径向平移，并按解剖系统分层（regional-anatomy=0、muscular=1、skeletal=2、cardiovascular/lymphatic/respiratory/digestive/urinary=3、nervous/endocrine/reproductive=4，每层额外位移 = 人体包围球半径 × 0.17）；体表外壳 `body-shell`（236 网格）在进度 0→0.4 渐进隐去，≥0.4 后不可见并被移出射线层。位移由进度重算、**从不累加**（0→1→0→1 可复现），相机随位移后包围盒联动取景。实测可见网格数 984 → 748，且拆解后仍可点选（50% 一次命中心脏、100% 一次命中脾脏）。**V2.1（2026-10-16）**：拆解进度改由**滚轮**驱动（人体总览未选中时，每格 0.07、钳制 [0,1]，向下拆、向上合；此时原生缩放关闭并在 canvas 捕获阶段拦 wheel，只作用于三维舞台，右侧知识栏滚动不受影响；选中结构后滚轮回交 OrbitControls）；**桌面端不再显示拆解滑杆**（`@media (hover: hover) and (pointer: fine)` 下 `display:none`，触屏保留）；默认人体**中性化公开展示**（隐去 `reproductive` 系统与体表外壳对应几何共 17 个网格，可见网格 984 → 967）。

**结构归并与可读名规则**。模型中有大量未登记中文名的细分结构；同一器官下的细分结构归并成该器官一项；能映射到作品实体的结构显示中文名，其余显示**真实解剖英文名**（属科学术语，可以展示）；**内部 ID（如 `body-shell`）一律不展示**。更细的结构可直接在模型上点选，右纸条给出真实结构名且同样不泄漏内部 ID。

### 3.4 关键技术二：程序化细胞几何（原创）

神经元与白细胞的三维形态完全由本工程按确定性伪随机参数生成，包含胞体、多级树突、长轴突、分段髓鞘、分叶核等结构，并暴露与领域实体一一对应的可选中部件。这样既规避了第三方细胞模型的许可风险，也保证了部件与视觉的可控性。

细胞模型各向异性强，作品用**确定性变换**把模型装进统一可视半径，保证默认机位能完整取景；结构热点采用「**普通 DOM + 每帧投影**」实现，既保证可点击、可 Tab 聚焦、可被读屏朗读，也避免依赖第三方库的隐式剔除导致标注消失。

### 3.5 关键技术三：数据完整性护栏

**70 项**单元测试（`domain` 22 + `cellGeometry` 19 + `fullBody` **28**，其中 4 项为 V2.1 新增）覆盖来源完整性、实体与关系一致性、内容资产脚本可达性、检验题有效性（含「不得考数字记忆」）、细胞几何取景，以及拆解位移确定性、外壳不透明度边界、解剖分层次序，与 **V2.1 的公开展示过滤（中性化默认人体，含 `GLTFLoader` 节点名清洗后的归一化匹配）**，把「不许造假」从口号变成可执行的检查。关键断言包括：**不存在「所有器官 → 任意细胞」的兜底关系**；心脏→白细胞必须是 `circulates_through` 且描述含「并不生成」；跨尺度步骤的目标必须真的有程序化模型。

## 六、项目总结

### 6.1 已完成

一个空间工作台（中央唯一真实三维人体 + 右侧一条随选中联动的知识纸条）、启动封面闸门、四层尺度的模型与内容、真实几何拆解（含拆解后仍可点选；**V2.1 改由滚轮驱动、桌面端无滑杆**）、**V2.1 选中「高亮 + 其余淡化」与取消选中恢复原视角**、**V2.1 默认人体中性化公开展示（隐去 17 个网格）**、两条完整贯通链路（脑→神经元、脾脏→白细胞）与一条循环功能关联（心脏↔白细胞）、14 条语义化关系、3 套共 29 步科普脚本与 6 道带解释和来源的检验题（作为内容资产保留）、70 项自动化测试与 11 页真实浏览器验收。

### 6.2 主要技术难点与处理

1. **解剖数据与科普叙事之间的落差** —— 通过「取景按真实网格包围盒计算」与「关系类型化」解决；过程中发现 atlas 里器官节点多为无自身几何的分组节点，`position` 也不在渲染坐标系中，因此改为**选中并请求聚焦**、由舞台决定机位，而不是在外部推算坐标。
2. **需求四「真实拆解」** —— 第三方查看器封装不支持网格位移，故自建 R3F 舞台直接读取 GLB `extras`，按解剖系统分层对真实网格做径向平移 + 体表外壳渐进隐去；位移由进度重算、从不累加，并用「单组半径上限 + 相机随位移后包围盒联动」双重护栏避免拆解时人体飞出画面。
3. **多尺度切换的画面稳定性** —— 通过「路由不拆分组件树」让三维场景在整段探索中保持挂载，切换页面不重新加载、不重新聚焦。
4. **三维与首屏体积的冲突** —— 通过按需加载把三维运行时拆成独立分块，使封底 `/about` 完全不承担三维体积（实测该页 `canvas = 0`）。

### 6.3 不足与后续升级

移动端真机验收与真实 GPU 性能数据待补；拆解的产品级视觉分离仍在打磨（内部层间距可继续加大）；组织层（tissue）目前以文字与上层结构呈现，不做体渲染；**V2.1 未做连续跨尺度转场**（现为「镜头推进 + 明确的继续深入入口」）；**V2.1 肾 / 膀胱未新增专题**（真实模型里 `urinary` 仅 3 个网格）；**中性化属中性化展示而非无性征人体，骨盆近观可见被移除外壳后露出的真实肌肉 / 骨盆结构**；若时间允许，可扩展胰腺 → 胰岛 β 细胞路线（需先获得许可明确的专用细胞模型，在此之前不使用普通动物细胞冒充）；全局搜索与模型对比留作后续能力。演示视频已按 V2.1 重录 `delivery/demo/bodyday-v2-walkthrough.mp4`（81 秒），如需更高规格版本可按 `delivery/demo/DEMO_VIDEO_SCRIPT.md` 在装有真实 GPU 的机器上重录；作品尚未在任何平台提交。

### 6.4 科学边界

BodyDay 是健康科普作品，**不构成医疗建议**；三维模型为科普示意，不按真实比例，标注点未与模型做逐点配准；所有关键知识均标注来源编号，完整来源表见作品「关于」页与 `SOURCES.md`（19 条，均于 2026-10-14 实测可达性）。
